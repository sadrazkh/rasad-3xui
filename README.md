# رصد | Rasad for 3x-ui

داشبورد فارسی، راست‌به‌چپ و قابل نصب روی Ubuntu برای آمار مصرف کاربران 3x-ui؛ با انتخاب کاربران، سیاست ثبت دامنه، نمودار زمانی، گزارش CSV/JSON، تاریخچهٔ تغییرات و ورود مدیر.

**این پروژه یک سرویس مستقل کنار 3x-ui است.** ترافیک کاربران از داشبورد عبور نمی‌کند. پایگاه داده و اطلاعات اتصال روی همان سرور می‌مانند. پیش‌نمایش میزبانی‌شده فقط دادهٔ نمونه دارد.

## نصب یک‌خطی روی Ubuntu

Ubuntu 22.04/24.04 یا جدیدتر، Python 3.10+ و systemd لازم است. نصب‌کننده Python و tzdata را از مخازن سیستم نصب می‌کند.

```bash
curl -fsSL https://raw.githubusercontent.com/sadrazkh/rasad-3xui/main/install.sh | sudo bash
```

نصب‌کننده نشانی کامل پنل 3x-ui (شامل `webBasePath`)، توکن API یا نام کاربری/رمز پنل، حساب مدیر رصد و مسیر اختیاری `access.log` را می‌پرسد. رمزها در ترمینال نمایش داده نمی‌شوند. رمز مدیر با scrypt ذخیره می‌شود؛ توکن/رمز اتصال 3x-ui باید برای اتصال مجدد قابل خواندن باشد و در فایل `root:rasad 0640` قرار می‌گیرد.

در اجرای اول، آمار مصرف فعال و ثبت دامنه خاموش است. نصب پایه Xray را جایگزین یا ری‌استارت نمی‌کند. در اجرای مجدد تنظیمات حفظ و از SQLite نسخهٔ پشتیبان گرفته می‌شود؛ رصد برای ارتقا دوباره اجرا می‌شود.

نصب از سورس دانلودشده:

```bash
git clone https://github.com/sadrazkh/rasad-3xui.git
cd rasad-3xui
sudo bash install.sh
```

## دسترسی به پنل

سرویس پیش‌فرض فقط روی `127.0.0.1:8787` گوش می‌دهد. برای استفادهٔ سریع، روی کامپیوتر خودتان:

```bash
ssh -L 8787:127.0.0.1:8787 root@YOUR_SERVER
```

سپس `http://localhost:8787` را باز کنید. مقدار `public_origin` پیش‌فرض همین است. اگر `127.0.0.1` را در مرورگر استفاده می‌کنید، مقدار را دقیقاً `http://127.0.0.1:8787` قرار دهید. این مقدار برای کنترل Origin درخواست‌های مدیریتی لازم است.

برای دسترسی دائمی، نمونهٔ [Nginx](deploy/nginx.conf) را با دامنه و گواهی معتبر خودتان تنظیم کنید و `public_origin` را برابر `https://YOUR_DOMAIN` بگذارید. Nginx و گواهی را نصب‌کننده به‌طور خودکار تنظیم نمی‌کند؛ دامنه در این پروژه مشخص نشده است. کوکی ورود روی HTTPS به‌صورت Secure صادر می‌شود.

```bash
sudo rasad status
sudo rasad logs
sudo rasad configure
sudo rasad restart
```

مسیرها: برنامه `/opt/rasad`، تنظیمات `/etc/rasad/config.json`، SQLite و پشتیبان‌ها `/var/lib/rasad`، سیاست ماژول مقصد `/run/rasad/policy.json`.

## چه چیزی واقعاً اندازه‌گیری می‌شود؟

| گزارش | نصب پایه | با ماژول اختیاری Xray |
|---|---|---|
| آپلود/دانلود هر کاربر و سقف کانفیگ | شمارنده‌های 3x-ui | همان منبع |
| مصرف امروز، دیروز و روند زمانی | اختلاف شمارنده‌ها از زمان نصب | همان منبع |
| دامنهٔ مقصد و تعداد اتصال | `access.log` موجود، اگر نام دامنه و email را داشته باشد | مقصد Dispatch در مسیرهای پشتیبانی‌شده |
| حجم هر مقصد | **در لاگ استاندارد موجود نیست** | بایت‌های payload عبوری از Dispatcher؛ مشاهدهٔ واقعی، با پوشش محدود |
| URL کامل، صفحهٔ بازدیدشده، پیام یا محتوای HTTPS | ثبت نمی‌شود | ثبت نمی‌شود |

DNS منبع اندازه‌گیری حجم نیست. از تعداد اتصال یا DNS، مقدار گیگابایت برای سایت تخمین زده نمی‌شود. اتصال به دامنه ممکن است مربوط به CDN، برنامه، preload یا فعالیت پس‌زمینه باشد و اثبات بازدید آگاهانهٔ صفحه نیست.

شمارنده‌های هر کاربر اندازه‌گیری‌شده هستند. تقسیم مصرف نزدیک مرز ساعت/روز، در فاصلهٔ نمونه‌برداری با فرض توزیع یکنواخت انجام می‌شود. اگر شمارنده کاهش پیدا کند، رخداد ریست ثبت و مبنای جدید گرفته می‌شود؛ ترافیک گم‌شدهٔ قبل/حین ریست قابل بازیابی نیست. آمار قبل از نصب از عدد تجمعی قابل استخراج نیست. هنگام قطعی، آخرین داده با هشدار نمایش داده می‌شود. خروجی دامنه‌ها حداکثر ۱۰۰ مقصد پرتکرار بازه را دارد.

## انتخاب کاربران و فعال‌سازی برای همه

در «مدیریت ثبت دامنه»، خود مدیر تیک کاربر را فعال می‌کند و درخواست او برای دریافت گزارش را تأیید می‌کند. دکمهٔ گروهی کاربران فعلی را تأیید می‌کند؛ کاربران آینده نیاز به تأیید جداگانه دارند. تنظیم «همه» یعنی همهٔ کاربران دارای تأیید. تیک‌ها، سیاست کلی و کلید فعال بودن ثبت، هم‌زمان اعمال می‌شوند.

خاموش‌کردن تیک، گزارش دامنه و حجم مقصد کاربر را از SQLite حذف می‌کند. خاموش‌کردن کلید کلی فقط جمع‌آوری را متوقف می‌کند و تاریخچه تا پایان مدت نگهداری باقی می‌ماند. سیاست ماژول هر ۵ ثانیه خوانده می‌شود؛ فایل snapshot ممکن است تا ۱۵ ثانیه به‌روز شود. قطع سرویس رصد پس از انقضای سیاست، ثبت ماژول را متوقف می‌کند.

**تیک‌ها روی ثبت در رصد اثر دارند.** اگر access.log سراسری Xray از قبل روشن باشد، Xray ممکن است همچنان لاگ کاربران دیگر را روی فایل اصلی بنویسد. رصد آن رکوردها را ذخیره نمی‌کند و لاگ خام را تغییر نمی‌دهد. برای کاهش سربار و ثبت در مبدأ، می‌توانید از ماژول اختیاری استفاده کنید و تنظیم لاگ اصلی را مستقلاً مدیریت کنید.

## راه‌اندازی گزارش دامنه در نصب پایه

مسیر یک `access.log` موجود را هنگام نصب وارد کنید. نمونهٔ بخش تنظیم لاگ Xray:

```json
{
  "log": {
    "access": "/var/log/xray/access.log",
    "error": "/var/log/xray/error.log",
    "loglevel": "warning"
  }
}
```

این تنظیم را در بخش تنظیمات Xray خود 3x-ui اعمال کنید. تغییر تنظیم Xray ممکن است به ری‌استارت هسته نیاز داشته باشد؛ نصب‌کننده آن را انجام نمی‌دهد. داشتن `email` یکتا برای کاربر لازم است. IP مقصد به اسم سایت تبدیل نمی‌شود. در صورت نیاز به نام دامنه، تنظیم sniffing خود Xray باید با پروتکل و نیاز شما سازگار باشد؛ روشن‌کردن sniffing می‌تواند سربار و تأخیر اولیه ایجاد کند.

`log_timezone` باید با منطقهٔ زمانی فرایند Xray برابر باشد (روی بسیاری از سرورها UTC). زمان گزارش همیشه تهران است. خواندن از انتهای فایل آغاز می‌شود؛ تاریخچهٔ قبل از شروع یا قبل از فعال‌سازی کاربر وارد نمی‌شود. جابه‌جایی و کوتاه‌شدن فایل تشخیص داده می‌شود؛ لاگ‌ها را با rename/create بچرخانید. با `copytruncate` در بار زیاد ممکن است بخشی از خطوط بین دو نوبت خواندن از دست برود.

نصب‌کننده برای فایل موجود، ACL خواندن کاربر سیستم `rasad` را تنظیم می‌کند. بعد از ساخت فایل جدید در logrotate، ACL را دوباره اعمال کنید:

```bash
sudo setfacl -m u:rasad:r /var/log/xray/access.log
```

اگر لاگ در `/root` یا `/home` باشد، محدودیت `ProtectHome=true` سرویس مانع دسترسی می‌شود؛ مسیر `/var/log/xray` را انتخاب کنید. وضعیت فایل در صفحهٔ تنظیمات دیده می‌شود.

## ماژول اختیاری حجم مقصد

سورس و راهنمای کامل در [xray-module](xray-module/README.md) است. این قابلیت نیاز به ساخت هستهٔ سفارشی و نصب جداگانه دارد. **این بخش آزمایشی است؛ نصب پایه آن را فعال نمی‌کند.** روی نسخهٔ ثابت upstream، آزمون شمارش، قطع ثبت و سقف حافظه و کامپایل در CI تعریف شده است. موفقیت CI جایگزین آزمون پروتکل‌های واقعی سرور شما نیست.

این ماژول بایت payload عبوری را ثبت می‌کند، نه تمام بایت‌های کارت شبکه و نه تأیید تحویل به مقصد. TCP با دامنهٔ معلوم، UDP نامشخص، مقصد IP نامشخص، سقف تعداد رکوردها، اولین snapshot به‌عنوان baseline و اتصال‌های قدیمی همگی محدودیت‌های پوشش دارند. جمع حجم مقصدها لزوماً برابر کل حجم کانفیگ نیست. هر محدودیت در راهنمای ماژول مشخص شده است.

## سربار و نگهداری

- پنل 3x-ui روی لوپ‌بک خوانده می‌شود؛ اطلاعات کانفیگ/UUID/لینک اشتراک به مرورگر فرستاده یا در SQLite ذخیره نمی‌شود. پنل جدید از مسیر `list/slim` استفاده می‌کند؛ نسخه‌های قدیمی از `list`.
- فاصلهٔ دریافت ۶۰، ۱۲۰ یا ۳۰۰ ثانیه است. بازرسی مرورگر درخواست مستقیم به 3x-ui نمی‌فرستد. بعد از تشخیص نسخه، هر چرخه معمولاً دو درخواست API دارد.
- سقف خواندن لاگ ۵۱۲ KiB در هر چرخه؛ شمارنده‌های مصرف محدود به باکت‌های ساعتی و نگهداری ۳/۷/۱۴/۳۰ روز هستند. رویداد مدیریت ۳۰ روز حفظ می‌شود. پاک‌سازی هر ۳۰ چرخه و هنگام تغییر مدت انجام می‌شود.
- سرویس systemd سقف ۲۵۶ MiB حافظه و ۲۰٪ یک CPU دارد. این سقف تضمین تحمل هر تعداد کاربر نیست؛ روی سرور پرترافیک فاصلهٔ ۲ یا ۵ دقیقه و نگهداری کمتر انتخاب کنید. عقب‌ماندگی خواندن لاگ در پنل مشخص می‌شود.
- سربار CPU، دیسک و خواندن/نوشتن محلی صفر نیست. پروژه درخواست بازدید به سایت مقصد، DNS اضافی یا تغییر مسیر ترافیک کاربران ایجاد نمی‌کند. برای پنل خارج از همین سرور HTTPS لازم است و درخواست‌ها ترافیک شبکه خواهند داشت.

## توسعه و آزمون

فرانت‌اند HTML/CSS/JavaScript بدون build و وابستگی شبکه‌ای در زمان اجرا است. فونت Vazirmatn همراه مجوز OFL در سورس قرار دارد. بک‌اند از کتابخانهٔ استاندارد Python و SQLite استفاده می‌کند.

```bash
python3 -m unittest discover -s tests -v
node --check dist/app.js
bash -n install.sh xray-module/build.sh
```

برای پیش‌نمایش **نمونه**:

```bash
python3 -m http.server 8788 --bind 127.0.0.1 --directory dist
```

برای اجرای واقعی:

```bash
python3 backend/server.py --config /etc/rasad/config.json
```

سرور Python مسیر `runtime.json` را با حالت `live` پاسخ می‌دهد؛ قطع اتصال هرگز باعث جایگزینی مخفی با دادهٔ نمونه نمی‌شود.

## منابع و سازگاری

با دو شکل `settings` (JSON object و JSON string) و مسیرهای قدیم/جدید آنلاین سازگار است. در نسخهٔ جدید، شمارندهٔ یک کاربر که به چند inbound متصل است دوباره جمع نمی‌شود. اگر یک email تکراری با شمارنده‌های متفاوت دیده شود، دریافت متوقف می‌شود تا گزارش غلط ثبت نشود. پنل‌هایی با login دارای 2FA بهتر است از توکن API استفاده کنند.

منابع قراردادهای upstream: [API احراز هویت 3x-ui](https://github.com/MHSanaei/3x-ui/blob/main/docs/content/docs/en/reference/api/authentication.mdx)، [API inbounds](https://github.com/MHSanaei/3x-ui/blob/main/docs/content/docs/en/reference/api/inbounds.mdx)، [شمارنده‌های Xray](https://xtls.github.io/en/config/stats.html)، [ساختار access log](https://github.com/XTLS/Xray-core/blob/main/common/log/access.go)، [Dispatcher](https://github.com/XTLS/Xray-core/blob/main/app/dispatcher/default.go).
