# ماژول اختیاری اندازه‌گیری مقصد — آزمایشی

این ماژول مستقیماً حجم payload ورودی/خروجی لینک Dispatcher را برای email و مقصد ثبت می‌کند. DNS، access.log و تعداد اتصال در محاسبهٔ حجم دخالت ندارند. تنها عدد بایت اضافه می‌شود؛ بافر ترافیک کپی یا ذخیره نمی‌شود و اتصال شبکه‌ای جدید ساخته نمی‌شود.

**به هستهٔ سفارشی نیاز دارد.** پنل 3x-ui استاندارد شمارندهٔ حجم هر دامنه را ارائه نمی‌کند. نصب معمول داشبورد، هستهٔ جاری را تغییر نمی‌دهد. روی نصب native پشتیبانی‌شدهٔ Ubuntu می‌توانید ماژول را با `sudo rasad sites enable` فعال کنید؛ این فرمان نسخهٔ فعلی را بررسی می‌کند، همان نسخه را با ماژول می‌سازد، پشتیبان می‌گیرد و هستهٔ سفارشی را مستقر می‌کند. `sudo rasad sites status` وضعیت و `sudo rasad sites disable` بازگشت به باینری پشتیبان را انجام می‌دهند. محدودیت‌های نصاب و دستور یک‌خطی `--sites` در README اصلی آمده است. Docker به تنظیم دستی نیاز دارد.

## ساخت

Git، Python و Go متناسب با `go.mod` نسخهٔ upstream را از منابع رسمی نصب کنید. مرجع پیش‌فرض، commit ثابت `c77a4d0e4932a53f3eeafafdfef877b56fd660ad` از مخزن رسمی Xray است و Go 1.27 می‌خواهد.

```bash
bash xray-module/build.sh
```

برای نسخهٔ Xray سرور خود می‌توانید tag/commit موجود را صریحاً بدهید؛ این حالت باید جداگانه کامپایل و آزمون شود:

```bash
bash xray-module/build.sh YOUR_XRAY_TAG /tmp/rasad-xray-build
```

می‌توانید مسیر Go رسمی را هم صریح تعیین کنید؛ `gofmt` از همان پوشه برداشته می‌شود یا با `RASAD_GOFMT` تعیین می‌شود:

```bash
RASAD_GO=/usr/local/go/bin/go GOTOOLCHAIN=local \
  bash xray-module/build.sh YOUR_XRAY_TAG /tmp/rasad-xray-build
```

نصاب برای استفاده از checkout رسمی، پاک و از قبل دریافت‌شده، `RASAD_EXISTING_SOURCE=1` را همراه همین دو آرگومان می‌دهد. اسکریپت origin رسمی و تطابق commit با ref درخواستی را پیش از تغییر بررسی می‌کند. `apply.py` اگر قرارداد مقصد پس از sniffing، شمارندهٔ native یا محل Dispatch تغییر کرده باشد متوقف می‌شود. خروجی `xray-rasad` و `xray-rasad.version.txt` فقط در پوشهٔ build ساخته می‌شوند. اجرای مستقل `build.sh` هستهٔ جاری را جایگزین نمی‌کند. سازگاری تمام نسخه‌ها، پروتکل‌ها و گزینه‌ها ادعا نمی‌شود.

## اتصال به رصد

سرویس رصد سیاست کاربران تأییدشده را اتمیک در `/run/rasad/policy.json` می‌نویسد. Xray باید امکان خواندن این فایل و نوشتن snapshot در همین پوشه را داشته باشد. برای نصب استاندارد 3x-ui به صورت سرویس `x-ui`، این متغیرها را در override سرویس والد Xray تنظیم کنید:

```ini
[Service]
Environment=RASAD_POLICY=/run/rasad/policy.json
Environment=RASAD_METRICS=/run/rasad/domains.json
```

در Docker، همین متغیرها و مسیر bind-mounted مشترک لازم است. کاربر غیر root به گروه/ACL مناسب نیاز دارد. در نصب جدید، پوشهٔ `/run/rasad` متعلق به `rasad:rasad` و حالت 02750 دارد؛ SGID گروه فایل snapshot را حفظ می‌کند. نوشتن ماژول با root یا عضویت/ACL مجاز انجام می‌شود. اگر Xray با کاربر دیگری اجرا شود، فایل snapshot باید برای گروه rasad خواندنی باشد (0640).

برای استقرار دستی، نام واقعی سرویس، مسیر باینری و شیوهٔ اجرای Xray را قبل از جایگزینی بررسی کنید. `ExecStart` والد، خروجی `ps` و `systemctl cat x-ui` به تشخیص کمک می‌کنند. از باینری اصلی کپی پشتیبان بگیرید، باینری سفارشی را ابتدا روی یک کانفیگ و کاربر آزمایشی اجرا کنید، و راه بازگشت را نگه دارید. به‌روزرسانی هسته از داخل 3x-ui می‌تواند باینری سفارشی را بازنویسی کند.

## دقت و پوشش

- شمارش بر اساس payload لینک Dispatcher است؛ framing تونل، سربار IP/TCP، retransmission و همهٔ بایت‌های رابط شبکه در آن نیست. شمارندهٔ down مثل `SizeStatWriter` پیش از نوشتن ثبت می‌شود؛ عدد تأیید تحویل موفق به کاربر نیست.
- نام مقصد TCP از همان مقصد dispatch پس از sniffing موجود به‌دست می‌آید. در `routeOnly: true` نیز مقصدِ مشاهده‌شده نام دامنه دارد، درحالی‌که `Target`/`OriginalTarget` برای اتصال IP اصلی را نگه می‌دارند؛ ماژول مسیر اتصال را تغییر نمی‌دهد. ماژول sniffing جدید فعال نمی‌کند. مقصد IP بدون دامنهٔ شناسایی‌شده به `__unknown_tcp__` می‌رود؛ DNS به‌صورت جداگانه اجرا نمی‌شود.
- UDP ممکن است در هر بافر مقصد متفاوت داشته باشد و پاسخ‌ها معمولاً فقط IP منبع دارند. بنابراین **همهٔ UDP، از جمله QUIC، فعلاً در `__unknown_udp__` جمع می‌شوند**، حتی اگر sniffing نام دامنهٔ اولین بسته را پیدا کرده باشد. انتساب کل این حجم به دامنهٔ نخست قابل اتکا نیست. ECH، VPN تو‌در‌تو و برخی پروتکل‌ها نیز دامنهٔ واقعی را پنهان می‌کنند؛ نام بیرونی قابل مشاهده، مدرک بازدید یک صفحهٔ خاص نیست.
- لینک بیرونی Mux با مقصد `v1.mux.cool` کنار گذاشته می‌شود؛ شمارش فقط در لینک‌های داخلی دارای هویت انجام می‌شود. علامت context از شمارش دوباره در dispatchهای متوالی جلوگیری می‌کند. پوشش Mux/XUDP و پروتکل‌های سرور باید در آزمون واقعی بررسی شود.
- لینک فقط هنگام ایجاد، برای کاربر تأییدشده wrapper می‌گیرد. بعد از فعال‌سازی یا فعال‌سازی مجدد، اتصال‌های قدیمی ممکن است تا reconnect پوشش نداشته باشند. غیرفعال‌کردن، policy را فوراً در داشبورد و حداکثر ظرف چرخهٔ ۵ ثانیهٔ ماژول اعمال می‌کند.
- سقف ۱۰۲۴ کاربر در policy، طول حداکثر ۳۲۰ بایت برای شناسهٔ email و ۸۱۹۲ رکورد email/مقصد است. خواندن policy به ۱ MiB محدود است. پس از سقف رکوردها، ترافیک عبور می‌کند اما flow جدید ثبت نمی‌شود. `dropped_flows` این کمبود پوشش را نشان می‌دهد؛ برای flow حذف‌شده، حجم ساختگی تولید نمی‌شود. این یک شمارندهٔ lifetime در فرایند است، تا restart هسته.
- snapshot هر ۱۵ ثانیه با فایل موقت تصادفی و نوشتن اتمیک محلی منتشر می‌شود. `started_at` زمان شروع فرایند و `first_ts` زمان اولین ایجاد رکورد نسل/دامنه را می‌دهند؛ بک‌اند می‌تواند اولین snapshot معتبر و مطابق نسل تأیید کاربر را وارد گزارش کند. برای snapshot قدیمی بدون زمان‌های معتبر، baseline امن استفاده می‌شود و حجم کنارگذاشته‌شده آشکار است. آخرین چند ثانیه در crash ممکن است از دست برود. رصد هر ۱/۲/۵ دقیقه اختلاف را وارد SQLite می‌کند؛ تقسیم زمانی در مرز ساعت تقریبی است.
- اگر سیاست حذف، نامعتبر یا منقضی شود، ماژول ثبت را متوقف می‌کند و مسیر عبور کاربران ادامه دارد. شمارنده‌های لینک‌های حذف‌شده بازفعال نمی‌شوند؛ پس از بازگشت سیاست، اتصال مجدد برای پوشش آن لینک‌ها لازم است. خطای نوشتن snapshot هم ترافیک را متوقف نمی‌کند.

بنابراین جمع حجم مقصدها تضمیناً برابر کل کانفیگ نیست. این ابزار آمار **مقصدهای پشتیبانی‌شده و پوشش‌داده‌شده** می‌دهد، نه تاریخچهٔ قطعی صفحات و نه حجم دقیق فیزیکی هر وب‌سایت.

| جریان | انتساب حجم در نسخهٔ فعلی |
| --- | --- |
| TCP با دامنه در درخواست کانفیگ | payload ارسال/دریافت به نام همان دامنه و کاربر |
| TCP با HTTP Host یا TLS SNI شناسایی‌شده توسط sniffing فعلی | payload به نام دامنهٔ مشاهده‌شده؛ `routeOnly` هم پشتیبانی می‌شود |
| TCP فقط با IP، یا sniffing خاموش/ناموفق/استثناشده | `__unknown_tcp__` |
| UDP، QUIC و XUDP | `__unknown_udp__`؛ تفکیک سایت ادعا نمی‌شود |
| Mux | carrier بیرونی حذف می‌شود؛ لینک داخلی دارای email مستقل شمرده می‌شود؛ پوشش واقعی هر پیکربندی باید آزموده شود |
| ECH یا تونل تو‌در‌تو | تنها مقصد بیرونی قابل مشاهده یا unknown؛ مقصد داخلی تضمین نمی‌شود |

طبق [مستندات رسمی Xray](https://xtls.github.io/en/config/inbound.html)، `destOverride` پروتکل‌های HTTP/TLS/QUIC را مشخص می‌کند و `routeOnly` نامِ شناسایی‌شده را برای مسیریابی استفاده می‌کند. `metadataOnly: true` از payload برای کشف Host/SNI استفاده نمی‌کند. رصد این تنظیمات را خودکار تغییر نمی‌دهد؛ فعال‌کردن sniffing در 3x-ui به انتخاب مدیر است و خودش سربار پردازشی دارد.

## آزمون

آزمون Go شمارش payload، حفظ نوع native برای شمارندهٔ splice، حفظ آمار 3x-ui پس از reset/disable، قابلیت TimeoutReader، جداشدن دو کاربر، زمان اولین snapshot، سیاست نامعتبر، بازگشت سیاست مفقود، فایل موقت symlink و سقف رکورد را بررسی می‌کند. CI روی مرجع ثابت، ماژول را کامپایل می‌کند و fixture واقعی VLESS روی loopback اجرا می‌کند: بایت دقیق TCP با دامنه، TCP فقط IP، HTTP sniffing با `routeOnly`، UDP در unknown، کاربر انتخاب‌نشده و خاموش‌کردن policy. همان snapshot واقعی از بک‌اند و SQLite عبور می‌کند و حجم ارسال/دریافت و تفکیک دامنه/unknown در report وب بررسی می‌شود. این fixture TLS/QUIC/Mux یا splice واقعی را شبیه‌سازی نمی‌کند. مسیر splice با قرارداد upstream و آزمون مستقیم شمارنده پوشش دارد؛ benchmark throughput انجام نشده است.

روی سرور خودتان با یک کاربر آزمایشی، پروتکل‌های واقعی، UDP، Mux، قطع policy و فایل ناموجود را بررسی کنید و CPU/RAM/throughput را قبل و بعد مقایسه کنید. ماژول هیچ payload را کپی یا ذخیره نمی‌کند و فقط طول بافر و شمارنده را پردازش می‌کند؛ سربار CPU و I/O محلی صفر یا افت throughput صفر ادعا نمی‌شود.
